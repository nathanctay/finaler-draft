## Why this scope exists

`plan.md`'s "Subscription and billing architecture": entitlements derive from webhooks, never
from the client, because the Checkout success redirect is not proof of payment. The authoritative
flow is `Stripe webhook -> signature verification -> event dedupe -> subscriptions table -> API
authorization check`. This slice builds everything up to and including the `subscriptions` table.
It deliberately does not build Checkout Session creation, the Customer Portal, entitlement
enforcement, free-tier limits, the lapse flow, or any UI -- those are later slices and change no
user-visible behaviour today.

## Raw-body scoping: how, and how it's proven

Fastify's plugin encapsulation is what makes "scoped to one route" possible: `addContentTypeParser`
called inside a child `app.register(async (scoped) => { ... })` callback shadows the parent's
default JSON parser only for routes registered on `scoped` itself. This is Fastify's own documented
pattern for exactly this problem (a Stripe/webhook-shaped route needing its raw body), not a
workaround invented for this slice. `app.ts`'s webhook registration reads:

```ts
await app.register(async (scoped) => {
  scoped.addContentTypeParser('application/json', { parseAs: 'buffer' }, (_r, body, done) =>
    done(null, body),
  );
  scoped.post('/api/webhooks/stripe', async (request, reply) => { ... });
});
```

**Proof, not just the comment claiming it:** `stripeWebhook.test.ts`'s "does not disable JSON
parsing anywhere else" test builds one app with the webhook route registered, then adds a second,
plain JSON-accepting route (`POST /api/test/echo-json`) directly on the same top-level `app`
instance -- outside the scoped child context -- and asserts its body arrives as a parsed object,
not a `Buffer`, while the webhook route on the same app instance still receives and correctly
verifies its raw bytes. I additionally mutation-tested the scoping itself (see below): moving the
`addContentTypeParser` call from `scoped` to the outer `app` variable broke both that test and,
more strongly than expected, the webhook route's own signature verification within that same test
run -- Fastify's encapsulation model does not tolerate a content-type parser being registered onto
a parent instance from inside a nested plugin callback the way this code is shaped. I did not fully
chase down Fastify's internal reason (avvio's plugin-loading order is not something I traced
line by line); the empirically-confirmed fact that matters is that breaking the scoping is caught
loudly, not silently.

## Out-of-order detection: what I chose and why

Stripe does not guarantee webhook delivery order, but does guarantee that each event's own
`created` field (a Unix timestamp) reflects generation order. Every write to the `subscriptions`
table stores the `created` timestamp of the event that produced it, in `last_event_created_at`,
and the upsert is a single atomic statement:

```sql
insert into subscriptions (...) values (...)
on conflict (user_id) do update set ...
where subscriptions.last_event_created_at < excluded.last_event_created_at
returning user_id
```

On a fresh insert there is no conflicting row to evaluate the `where` against, so it always
applies. On a conflict, Postgres evaluates the `where` per row and simply omits the row from
`returning` when it's false rather than updating it -- so an empty result reliably means "a later
event already won," distinguishable from every other outcome by `rowCount`. Ties (`created` equal)
do not apply, deliberately: Stripe's granularity is whole seconds, a same-second duplicate carries
no new information the store doesn't already reflect, and treating "not older" as sufficient to
apply would let two racing requests for the same second flap depending on arrival order, which is
exactly what this guard exists to prevent. `recordInvoiceEvent`'s update-only statement uses the
identical `and last_event_created_at < $eventCreatedAt` guard.

I considered and rejected reconciling directly from Stripe (a `GET` back to the API on every event)
as unnecessary for this slice: the event payload itself already carries everything needed to
project current state, and plan.md's instruction is specifically to reconcile "from the event's
subscription object," not to re-fetch it.

## IP allowlist: implemented, not skipped

plan.md asks for this as defence in depth but explicitly warns a hardcoded list will rot. I
researched whether a non-hardcoded source exists before deciding: Stripe publishes a live,
machine-readable list at `https://stripe.com/files/ips/ips_webhooks.json` (documented at
`docs.stripe.com/ips`; fetched directly and confirmed it returns Stripe's current published IPs),
with 7 days' notice of changes via their `api-announce` list. `stripeIpAllowlist.ts` fetches this
on a periodic background timer (default 6 hours -- comfortably inside that 7-day notice window)
and caches the result in memory.

**The failure-mode asymmetry is deliberate and is the whole point:** the allowlist fails _open_,
never closed. Before any successful fetch, `isAllowed` returns `true` unconditionally. If a
refresh fails after an earlier one succeeded, the previous good list is kept rather than cleared
or replaced with an empty set. Signature verification is what actually authenticates a webhook;
this allowlist is supplementary, and a broken supplementary check must never be able to reject a
legitimately signed event -- that would be strictly worse than not having the check, which is
exactly the failure mode plan.md warned against for a hardcoded list, and a periodic fetch that
fails open avoids it the same way a hardcoded list couldn't.

Wired into `server.ts`: started at boot (`ipAllowlist.start()`) only when Stripe is fully
configured, stopped in the app's `onClose` hook alongside the database pool.

## Mutation testing

Every behaviour load-bearing enough to matter was broken, confirmed to fail the _specific_ test it
should, then restored and reconfirmed green. All were run against the final state; each mutation
below was reverted immediately after confirming the failure, and the full relevant suite was green
again before moving to the next.

1. **Signature verification removed** (`stripe.client.webhooks.constructEvent(...)` replaced with
   a bare `JSON.parse` of the raw body). **This is the one that matters most.** Failed exactly the
   three tests that exist to catch it: "rejects a payload whose signature does not match,"
   "rejects a payload whose body was tampered with after signing," and "rejects a correctly signed
   payload whose timestamp is outside the tolerance window" -- each `expected 200 to be 400`. All
   18 other tests in the file stayed green, meaning the failure was specific, not a broad crash.
   Restored; 21/21 green.
2. **Dedupe disabled** (`markProcessed` hardcoded to always return `true`, so the `on conflict do
nothing returning id` insert still runs but its result is ignored). The fast, fake-store-backed
   unit tests in `stripeWebhook.test.ts` did **not** catch this -- expected and worth stating
   plainly: that fake store reimplements its own dedupe against an in-memory `Set`, so it can only
   prove `dispatchStripeEvent`/the route call the store correctly, never that the real SQL's dedupe
   actually works. The integration suite did catch it: "dedupes a repeated event.id into a single
   state change" failed (`expected 'stale' to be 'duplicate'` -- the second delivery reached the
   upsert and lost only to the out-of-order guard, not to dedupe) and "dedupes recordIgnoredEvent
   independently" failed the same way. This is exactly why the task asked for both unit and
   integration coverage, not either alone. Restored; both suites green.
3. **Out-of-order guard removed** (dropped the upsert's `where` clause). Failed exactly "does not
   move state backwards when an older event arrives after a newer one" (`expected 'applied' to be
'stale'`); every other integration test stayed green. Restored; 31/31 green.
4. **Raw-body scoping broken** (see above) -- registered the content-type parser on the parent
   `app` instead of the scoped child. Failed the scoping-proof test and, unexpectedly usefully,
   several others in the same file that reuse `buildWebhookApp()`, since the mutated registration
   broke that app instance's own webhook processing too. Restored; 21/21 green.
5. **IP allowlist check short-circuited off** (`if (false && stripe.ipAllowlist && ...)`). Failed
   exactly "rejects a request from an IP outside the configured allowlist"; the paired "allows a
   request whose IP the allowlist accepts" stayed green, as it should -- the mutation only removes
   the ability to _reject_. Restored; 21/21 green.
6. **`invoice.payment_failed` no longer mapped to `past_due`** (hardcoded the invoice-event status
   to always `'active'`). Failed exactly "projects invoice.payment_failed as a past_due update";
   the paired `invoice.paid` test stayed green. Restored; 21/21 green.
7. **`readUserId` never reads `metadata.userId`** (hardcoded to always return `null`). Failed 9 of
   21 tests -- every test whose scenario depends on a subscription actually resolving to a user,
   which is most of them; the tests scoped around _not_ resolving a user (`ignores`, `unresolved`)
   correctly stayed green. Restored; 21/21 green.
8. **Unrecognized subscription status silently coerced** instead of thrown (`toKnownStatus`
   short-circuited to `return status as SubscriptionStatus` unconditionally). Failed exactly
   "rejects an unrecognized subscription status." Restored; 21/21 green.

After every mutation was reverted, `git diff --stat` and `git status --porcelain` were checked to
confirm the working tree matched the intended change set exactly, with nothing left half-reverted.

## Known limitations / decisions for a later slice to pick up

- **Linking a Stripe customer to a Better Auth user depends on `subscription.metadata.userId`**,
  which only a future Checkout Session (`subscription_data.metadata.userId` or equivalent) can
  set -- Checkout Session creation is explicitly out of scope here. Until that slice exists, no
  real subscription event this webhook receives will resolve to a user on its _first_ event; the
  store's fallback (resolving from an existing row by `stripe_customer_id`) only helps _after_ the
  first successful resolution. This is a documented, deliberate scope boundary, not an oversight --
  see `stripeSubscriptions.ts`'s comment on `recordSubscriptionEvent`.
- **`invoice.paid`/`invoice.payment_failed` are update-only**, never creating a new
  `subscriptions` row. An invoice event doesn't reliably carry a priceId in this API version, and
  `customer.subscription.created` is what should establish the row in the first place; if an
  invoice event arrives before that (a real possibility under out-of-order delivery), it's a safe
  no-op rather than a partial/priceless row.
- **API version field relocations mattered and were verified against the installed SDK's own
  `.d.ts` files, not assumed from training knowledge**: `Subscription.current_period_end` no
  longer exists at the top level as of a 2025 API version change (it's per subscription item now),
  and `Invoice.subscription` is gone in favour of `invoice.parent.subscription_details.subscription`.
  Both are called out in `stripeWebhook.ts`'s doc comment specifically so a future reader isn't
  caught by the same relocation again.
- **Rate limiting**: the webhook route sits behind the existing global per-client cap
  (`@fastify/rate-limit`, keyed on `x-real-ip`) like every other `/api/*` route -- not given a
  dedicated, more generous budget for Stripe's own retry traffic. Worth revisiting if Stripe's
  legitimate retry volume is ever observed to approach that cap in production.
- **No test clocks / Stripe CLI local forwarding** were exercised (plan.md's "Testing" section
  mentions both) -- out of reach without live Stripe sandbox access from this environment. Coverage
  here is unit + integration + real-signature verification against the installed SDK's own crypto,
  not an end-to-end run against Stripe's actual test-mode infrastructure.
